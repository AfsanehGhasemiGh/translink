01 · OPENING STORY

What to say and show

“I am planning access to a Suncorp Stadium event. Which bus corridors are candidates? What would a Milton station closure affect? Could extra evening services reduce waiting, and would a delayed train break an interchange connection? We can explore those decisions using a shared transport model and see which answers are source facts versus planning assumptions.”
  1. Orient the planner: show Brisbane routes, stations and stops; focus on Suncorp Stadium. Explain that this is a selected network subset, not all Queensland.
  2. Find candidate corridors: open the protected app; Fabric SSO and its backend check run automatically. Once connected, select Use Q1 → Ask Fabric. Read the short route list and source citation; expand query details only if asked.
  3. Assess a closure: run Q2 for the rail service patterns that call at Milton. This is feed-wide exposure, not a dated operational disruption analysis. Open the V2 ontology graph to explain the connections.
  4. Explore alternatives: use Q3/Q4 or the scenario sliders. State clearly that these calculations use hypothetical inputs, not a date-specific network simulation.
  5. Close: “The value is a shared planning vocabulary and visible evidence. The next step toward operational planning is validated dated routing, transfer rules and demand data—not more confident AI wording.”
If Ask Fabric is disabled: it is waiting for automatic Fabric SSO/backend verification or an in-flight answer. When connected, extra login/retry controls are hidden. If an expired session or MFA requires interaction, use Continue with Fabric; for a service error use Retry connection and read the error. There is no separate backend password, and authentication is never bypassed.
02 · DATA PROVENANCE

Where did the information come from?

Transport source: Translink / Queensland Department of Transport and Main Roads, via the Queensland Government GTFS catalogue. The ingestion downloads the official South East Queensland GTFS ZIP.

Snapshot: imported 10 November 2026. The downloaded map feed reported coverage 10 November 2026–9 January 2027; that range does not mean every trip operates every day. This demo does not refresh automatically.

03 · DEPLOYED ARCHITECTURE

One Fabric app, two data paths

Data preparation: download official data → validate → store managed tables → bind business entities.

1. Translink GTFS ZIPPublic schedules, stops, trips, calendars. Static snapshot.
2. Fabric notebookTranslink_Ingest_GTFS downloads to Lakehouse Files, checks keys/joins and calculates venue proximity.
3. TranslinkNetworkManaged Delta tables in the Lakehouse; queried through its SQL analytics endpoint.
4. TranslinkTransportV28 entity types and 7 relationships bind business concepts to the source tables.

Live chat: a signed-in user asks a question → the hosted function invokes the ontology agent → the agent queries bound data → evidence returns to the UI.

1. Rayfin web UIProtected static hosting in Fabric. MapLibre renders the map. Fabric brokered sign-in gates access.
2. planner functionTyped Rayfin client invocation. Function runs in Fabric; resource tokens stay server-side.
3. V2 ontology agentMCP ask_ontology resolves entity context, queries the bound sources, and returns an answer with evidence.
4. Presenter / plannerReads the answer, source citations and returned evidence. Checks values against known data and limitations.

Map path: frontend's local GTFS geometry snapshot + external map tiles → browser map. What-if sliders: browser → deterministic arithmetic. Neither path is a live demand model.

What the ontology connects

Route → Trip → StopCall → Stop
Service → Trip and Service → ServiceException
Venue → VenueStopLink → Stop

These describe business relationships; physical joins can run from the foreign-key side toward the key side. Source data stays in the Lakehouse; the ontology supplies meaning and bindings.

Identity boundary: Fabric sign-in and app permission authorize the user to invoke the app. Under Rayfin application authentication, external Fabric queries run as the app item owner, not each visitor. This was explicitly approved for this public-data demo. It is not per-user row-level security on the external Lakehouse. Tokens are not returned to the browser.

Deployment: TranslinkPlannerApp is a Rayfin AppBackend item in the Translink workspace. The web UI and planner function are hosted in Fabric. App-owned database and storage services are disabled; the app reuses the existing Lakehouse and ontology. No Azure App Service was provisioned.

The earlier separate TranslinkPlanner data agent and original V1 ontology still exist for the optional legacy binding inspector. The deployed chat uses the V2 ontology directly, not that older agent.

04 · COPYABLE DEMO PROMPTS

Prove facts first. Then test assumptions.

In the app, Use Q1–Q4 loads the prompt; Copy Q1–Q4 copies it. The buttons here copy the same prompts for use in the app. Allow up to a few minutes for a live response; do not submit duplicate questions while one is running.

Q1 · Event access

Which buses could support a stadium event?

Which bus routes in our selected network have scheduled calls at stops within 1,200 metres straight-line of Suncorp Stadium? Show distinct route numbers and public route names, using Venue, VenueStopLink, StopCall, Trip and Route. These are candidates for event planning, not confirmed event services or walking access. Cite the source; put query details in Evidence.

Expected output: a deduplicated candidate bus-route list with public names and a proximity limitation.

“This identifies corridors worth investigating. The agent follows actual service calls, not just lines passing near the stadium. We still need walking links and a dated event timetable before treating these as usable event journeys.”

Evidence to show: Venue → VenueStopLink → StopCall → Trip → Route, filter to bus, deduplicate route IDs. VenueStopLink and StopCall connect through their shared Stop key. The 1,200-metre radius is straight-line.

Q2 · Closure exposure

What if Milton station closes?

If Milton station is unavailable, which selected rail service patterns would be affected? Use actual scheduled calls at Milton station platforms. Compute the total distinct rail route IDs over ALL matching routes BEFORE limiting displayed examples; do not count just the top five. Show that total and up to five public route-name examples. This is a hypothetical closure across the feed, not a dated disruption forecast. Do not invent replacement routes or passenger impacts. Cite sources; put query details in Evidence.

Expected output: the total distinct rail service patterns, counted before limiting to five examples. No invented passenger impact or replacement journey.

“We can identify the services exposed to a closure. This is not a prediction of cancellations: we must select a service date and model the actual closure and replacement plan before operational decisions.”

Evidence to show: Milton platform records → StopCall → Trip → rail Route. Deduplicate routes, not stop-call rows. Inspect station matching and service scope in the query.

Q3 · Extra event buses

Would extra evening buses reduce waiting?

For planning extra route 385 buses after a Suncorp Stadium event, assume the headway changes from 20 minutes to 10 minutes. How would expected waiting time and services per hour change? Assume uniform passenger arrivals and evenly spaced services. Clearly label the result hypothetical, not the actual event timetable, demand or fleet feasibility. Put calculations in Evidence.

Expected: waiting 20 ÷ 2 = 10 → 10 ÷ 2 = 5 minutes; services/hour 60 ÷ 20 = 3 → 60 ÷ 10 = 6.

“We now switch from retrieved facts to explicitly hypothetical inputs. This is reproducible arithmetic, not a dated timetable, fleet feasibility analysis or demand forecast.”

Evidence to show: input headways, assumptions and formula. Any source-table counts in the answer only establish context; they do not validate those hypothetical headways.

Q4 · Interchange reliability

Would a late train break a bus connection?

At Roma Street, assume a connecting bus departs 8 minutes after the planned train arrival, with zero transfer walking time and no holding. If the train arrives 10 minutes late, is that hypothetical connection still possible? Give the remaining margin and state what dated timetable and minimum-transfer information is needed to assess a real connection. Put calculations in Evidence.

Expected: 8 − 10 = −2 minutes; the hypothetical connection is missed by 2 minutes.

“The arithmetic is straightforward. A real assessment needs a service date, actual trips/stops, calendar exceptions, minimum transfer times and any holding rules.”

Evidence to show: assumed margin/delay, calculation, missing walking-transfer rules. The current scenario calculator is not date-aware and does not simulate network-wide impacts.

05 · LIVE WHAT-IF WALKTHROUGH

Event exit: better frequency, but a fragile connection

A one-minute script. Read the “Say” column while changing the controls.

DoSay
Select route 61 → What if?“Let's look at getting people home after a stadium event. These are assumptions we can change—not the current timetable.”
Set headways to 20 → 10 minutes.“What if we run buses every ten minutes instead of every twenty?”
Set arrival shift to 9; transfer window to 8. Compare.“Average waiting drops from ten minutes to five. But if a train arrives nine minutes late and the bus was due eight minutes after its planned arrival, the connection is missed by one minute.”
Change the transfer window to 12. Compare.“What if we allow twelve minutes between the train and bus? With the same delay, three minutes remain.”
Pause on the comparison.“So more frequent buses can reduce waiting, while a larger connection window gives us more room for delays. Before making a real change, we'd check the dated timetable, walking time and available buses and drivers.”
One sentence to remember: “We are comparing options, not predicting an actual journey.” Waiting assumes evenly spaced buses and passengers arriving uniformly. The margin excludes walking and holding.

Make the sensitivity visible

  1. Change arrival shift to 10 minutes and compare again: the hypothetical connection is missed by 2 minutes.
  2. Change the assumed transfer window to 12 minutes, keeping the 10-minute shift: the remaining hypothetical margin is 2 minutes. That is not proof of a usable transfer without walking/accessibility data.
  3. Return to Questions and use Q3/Q4 to discuss the same assumptions with the ontology agent. Q4 uses 10 minutes, so its two-minute result differs intentionally from the screenshot's nine-minute/one-minute example.

Where the information comes from: route names and map context come from the GTFS snapshot. Headways, arrival shift and transfer window come from the controls you set. The comparison is local deterministic arithmetic: expected wait = headway ÷ 2; services/hour = 60 ÷ headway; transfer margin = window − shift. It does not retrieve those values from Fabric or modify an operational timetable.

What the planner must validate next: a real service date and event finish time; active trip calendars and exceptions; actual stop times; minimum pedestrian-transfer/accessibility times; holding rules; vehicle/driver availability and passenger demand. None of those is established by adjusting these sliders.

“Use this as a transparent conversation about alternatives. We have not demonstrated that an actual train or bus connection will be missed, that a replacement service is feasible, or that these changes meet demand.”
06 · CONFIDENCE WITHOUT OVERCLAIMING

How do we check accuracy?

  • Data integrity: ingestion checks required files, nonempty/unique entity keys and relevant foreign-key relationships before writing managed tables. A manifest records source URL, import timestamp, archive SHA-256, schemas and readback counts.
  • Real deployment: Rayfin deployment and management health were confirmed. Browser tests exercised the protected sign-in gate and the actual hosted function—not just localhost.
  • Known-answer baseline: earlier retrieval checks returned 8 bus / 56 rail route IDs and 30 venue-stop links, matching independently recorded data. The planner-oriented questions above must additionally verify the service-call joins and station filters; baseline counts alone do not prove those answers.
  • Calculation tests: focused tests cover waiting-time arithmetic, transfer-margin boundaries, invalid input and the response-format bug. Eight unit tests and the frontend build passed before the latest guide update.
  • Visible evidence: show source tables, query text and returned evidence. It is an audit-oriented explanation, not private AI reasoning. The evidence panel can contain the agent's own answer rather than an independently signed execution log; a result filename or tool name alone is not proof of every claim.
  • No absolute guarantee: AI answers can be wrong or sources stale. Do not use the demo as operational transport advice without source-level reconciliation, validated routing/transfer rules and planner review.
Not in the demo: live vehicles, measured passengers/crowding, vehicle capacity, event service schedules, population/development overlays, verified walking paths, demand forecasts or a validated route optimizer. “Brisbane City Plan” data has not been ingested.

Three dates to distinguish: snapshot/import date; actual service date (calendar + exceptions); and hypothetical scenario inputs (no date). The ontology includes schedule context, but the local scenario arithmetic does not apply a service date.
